# Ключові рішення

## 1. Продуктове рішення

FocusLab — офлайн-перший desktop-застосунок для Windows, що об'єднує в одному вікні чотири функції, які користувач зазвичай розкидає по різних інструментах: Канбан-дошку задач, Pomodoro-таймер, швидкий запуск локальних/мережевих ресурсів і нотатки.

Головна проблема, яку вирішує продукт — розпорошення уваги між окремими застосунками (таск-менеджер, Pomodoro-сайт, файловий провідник) та залежність хмарних інструментів від мережі. FocusLab свідомо займає нішу «Focus Workspace Hub», а не ще одного універсального таск-менеджера.

**Цільові користувачі:**
- студенти з багатьма дедлайнами одночасно;
- розробники/фрілансери, яким потрібен облік фокус-часу для білінгу;
- організатори заходів з великою кількістю дрібних задач.

## 2. Технологічний стек і архітектурні рішення

| Рішення | Що саме | Обґрунтування |
|---|---|---|
| Платформа | Windows Desktop, .NET 8 | Нативна продуктивність без залежності від Electron-подібних прошарків |
| UI-фреймворк | WPF + патерн **MVVM** | Чітке розділення View/ViewModel через Data Binding; XAML дозволяє декларативно описувати кастомну Канбан-дошку та анімовані Pomodoro-індикатори; команди через `ICommand`/`RelayCommand` полегшують Unit-тестування |
| БД | SQLite, локальний файл | Відповідає вимозі Offline-First — жодних зовнішніх серверів |
| Доступ до даних — CRUD | **Entity Framework Core**, Code-First + міграції | Структура БД описується C#-сутностями (`Task`, `Project`, `FocusSession`), LINQ to Entities дає типобезпечні запити й автоматичний Change Tracking для update-операцій |
| Доступ до даних — звітність | **ADO.NET**, прямі SQL-запити (`GROUP BY`, `SUM`, `ExecuteReaderAsync`) | EF Core свідомо обійдено для модуля аналітики — щоб уникнути накладних витрат ORM при агрегації великої кількості записів |
| Паралелізм | Async/Await на всіх операціях з БД та файловою системою | UI не має блокуватися під час збереження чи побудови звіту |
| Локалізація | Українська мова, розширювана через `.resx` | Закладено одразу, а не як доробка |

**Ключове архітектурне рішення — розділення EF Core / ADO.NET за призначенням, а не за зручністю:** EF Core відповідає за звичайні CRUD-сценарії (задачі, ресурси, нотатки), а ADO.NET — виключно за агрегатну аналітику. Це свідомий компроміс «зручність розробки там, де це не критично» проти «продуктивність там, де важлива швидкість звіту».

## 3. Модель даних і бізнес-логіка

- **Pomodoro-сесія зараховується лише якщо завершена «природно».** Якщо сесія перервана вручну — вона не потрапляє у статистику й не записується в БД.
- **Лічильник перерв:** після кожної природно завершеної сесії перевіряється, чи це кожна 4-та сесія поспіль — якщо так, пропонується довга перерва, інакше коротка.
- **Задача не просувається автоматично по статусах через Pomodoro** — рух картки по дошці лишається окремою, ручною дією користувача (Drag & Drop), а не побічним ефектом завершення фокус-сесії.
- Offline-first перевіряється як перший крок use-flow (перший запуск застосунку відбувається офлайн), а не як окрема нефункціональна вимога збоку.
- Єдиний актор-людина в системі — **Користувач**, без ролей «адміністратор» чи «гість» на рівні основних сценаріїв.
- Quick Launcher і offline-старт змодельовані як пряма інтеграція з ОС Windows (відкриття файлів/папок через системні виклики), а не як внутрішня логіка застосунку.
- Модуль аналітики залежить від даних, зібраних Pomodoro-таймером — без зафіксованих сесій звітувати нічого.

## 4. Пріоритизація

Рішення пріоритизувати не за модулями, а за критичністю для життєздатності MVP:

- **Must Have:** офлайн-старт БД, створення задачі, Drag & Drop по дошці, миттєве відкриття ресурсу. Це мінімум, без якого немає демонстрованого продукту.
- **Should Have:** прикріплення ресурсів (файл/папка/URL), Pomodoro-сесії з перервами, фільтрація та підсвічування прострочених задач — розширюють UX, але не блокують перший запуск.
- **Could Have:** аналітика продуктивності — свідомо відкладена в кінець, бо вимагає вже наповненої даними БД і найскладніша технічно (ADO.NET-запити + графіки).
- **Won't Have (чітко визначено з самого початку):** хмарна синхронізація між пристроями, багатокористувацький режим / спільний доступ до дошок, інтеграція з зовнішніми календарями. Це рішення свідомо обмежити scope, щоб не розмивати ціннісну пропозицію «локальний і автономний».

Роадмап розробки повторює цей порядок: архітектура + базовий CRUD → інтерактивний UI + Quick Launcher → таймер + зручність → аналітика та оптимізація.


## 5. Дизайн

UI спроєктовано окремо у Figma до написання XAML-коду — рішення проєктувати інтерфейс заздалегідь, а не «на льоту» під час розробки.

## Підсумок

Ключові рішення проєкту: (1) offline-first WPF/.NET 8 застосунок без хмари й без акаунтів; (2) розподіл EF Core (CRUD) / ADO.NET (аналітика) за призначенням; (3) MoSCoW-пріоритизація, що свідомо відкладає аналітику й виключає мультикористувацькість і хмарну синхронізацію з поточного релізу; (4) бізнес-правило «незавершена Pomodoro-сесія не зараховується»; (5) єдиний актор-людина в системі. Головна розбіжність, яку варто усунути до розробки — наявність ролі «Адміністратор» і авторизації, що суперечить рішенню про однокористувацький локальний застосунок.
