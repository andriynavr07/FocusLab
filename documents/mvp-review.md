# Огляд MVP FocusLab

**Стек:** .NET 8 · WPF · EF Core · ADO.NET · SQLite

## 1. Ціль MVP

Локальний офлайн-застосунок, у якому користувач може: завести задачу → рухати її по Канбан-дошці → відкривати пов'язані ресурси → працювати по Pomodoro на задачі → бачити статистику часу.

## 2. Пропонований склад MVP

| # | Функція | US | Пріоритет | Обґрунтування |
|---|---------|----|-----------|---------------|
| 1 | Автостворення БД + міграції, офлайн-запуск | 5.1 | Must | Фундамент для всього іншого |
| 2 | Створення задачі (назва, пріоритет, дедлайн, проєкт) | 1.1 | Must | Ядро продукту |
| 3 | Канбан-дошка + Drag & Drop зі збереженням статусу | 1.2 | Must | Головний UX-елемент |

| 5 | Pomodoro-таймер для задачі + запис сесії в БД | 3.1, 3.2 (сесія + перерва 5 хв) | Must | Джерело даних для аналітики |

## 3. Прогалини в поточних User Stories

Що не описано, але без цього застосунок буде неповним:

1. **Редагування та видалення задач.** Є лише створення. Потрібні: редагування, видалення (із підтвердженням), видалення ресурсу з картки.
2. **Керування проєктами та тегами.** Історія 1.1 каже «існуючий проєкт», але немає історії створення/редагування/видалення проєктів і тегів. Без цього дропдаун проєктів порожній.
3. **Що робити з видаленим проєктом/тегом.** Каскад чи «Без проєкту»? Потрібно вирішити на рівні БД.
4. **Налаштування таймера.** Тривалість сесії/перерв зашита (25/5/15–20). Мінімум — константи в одному місці, краще — екран налаштувань.
5. **Несправжні сесії.** Що записувати при достроковій зупинці: нічого, чи сесію з `IsCompleted = false` і фактичною тривалістю? Це впливає на аналітику.
6. **Повернення задачі зі статусу «Виконано».** Чи очищати `CompletedAt`? У історії 1.2 не описано.
7. **Тег vs проєкт в аналітиці.** Одна задача може мати кілька тегів → час у діаграмі «за тегами» буде подвоєно. Варто розділити діаграму за проєктами (однозначно) і, за потреби, окремо за тегами з поясненням.
8. **Порядок карток усередині колонки.** Drag & Drop між колонками описано, порядок усередині колонки — ні. Для MVP можна сортувати за пріоритетом/дедлайном.
9. **Резервна копія/експорт даних.** Для офлайн-first застосунку втрата файлу БД = втрата всього. Не для MVP, але записати в backlog.

## 4. Технічні ризики

| Ризик | Що робити |
|-------|-----------|
| Таймер у «фоновому потоці» (US 3.1) | Не покладатися на лічильник тіків. Зберігати `startTime` і обчислювати залишок як різницю з `DateTime.UtcNow` — тоді згортання, затримки потоку та сон ПК не ламають відлік. Оновлення UI через `DispatcherTimer`. |
| Нативні Windows-сповіщення (US 3.2) | У WPF немає вбудованого API «з коробки». Потрібен NuGet-пакет (наприклад, `Microsoft.Toolkit.Uwp.Notifications`) і target framework `net8.0-windows10.0.xxxxx`. Перевірити на самому початку. |
| Drag & Drop у WPF | Немає готового Канбан-контролу. Закласти час на `DragDrop.DoDragDrop`, `AllowDrop`, візуальний фідбек. |
| Асинхронне збереження і `DbContext` | `DbContext` не потокобезпечний. Використовувати `IDbContextFactory` і короткоживучі контексти на операцію. |
| Холодний старт 2–3 с (US 5.1) | Міграції EF Core і перше звернення до контексту повільні. Виконувати ініціалізацію БД до показу головного вікна асинхронно, замірити час рано. |
| Змішування EF Core та ADO.NET | Одне підключення до SQLite-файлу з двох стеків: узгодити рядок підключення та режим журналу (WAL), щоб уникнути `database is locked`. |
| Час і часові пояси | Зберігати `DateTime` в UTC, показувати в локальному часі. Межі «сьогодні/тиждень/місяць» рахувати за локальним часом і переводити в UTC для запиту. |
| Шляхи ресурсів | Файли можуть зникнути. Перевірку існування робити при кліку (як у US 2.2), не при завантаженні дошки. |

## 5. Нефункціональні вимоги: що варто уточнити

- «Холодний запуск ≤ 2–3 с» — на якому ПК і при якому обсязі даних вимірювати? Запропонувати перевірку на БД зі 1000 задач і 10 000 сесій.
- «100% функціоналу в режимі "У літаку"» — це виконується автоматично, якщо не додавати мережевих залежностей (шрифти, іконки, графіки лише локальні). URL-ресурси відкриваються браузером і, звісно, потребують мережі.

## 6. Пропонований порядок розробки

1. **Каркас:** структура рішення (UI / Application / Infrastructure), MVVM, DI, SQLite + міграції, перший запуск.
2. **Задачі:** модель, CRUD, Канбан-дошка, Drag & Drop, збереження статусу.
3. **Ресурси:** сутність ресурсу, додавання трьох типів, відкриття з перевіркою існування.
4. **Pomodoro:** таймер, фокус-режим, запис сесії, сповіщення, коротка перерва.
5. **Аналітика:** ADO.NET-запити, вкладка, зведені показники.
6. **Друга ітерація:** теги та фільтри, пошук, підсвічування, діаграма, довга перерва.
7. **Полірування:** обробка помилок, перевірка холодного старту, тестування офлайн.

## 7. Критерії готовності MVP (Definition of Done)

- Сценарії SC-01 – SC-09 проходяться вручну без крашів.
- Дані переживають перезапуск застосунку.
- Застосунок працює без мережі.
- Немає блокування UI під час збереження й побудови звіту.
- Помилки файлової системи та БД показуються повідомленнями, а не аварійним завершенням.
