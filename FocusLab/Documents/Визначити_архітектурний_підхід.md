# Визначити архітектурний підхід

**Проєкт:** FocusLab — автономний (offline-first) десктопний застосунок для Windows
**Стек:** .NET 8 · WPF · MVVM · SQLite · EF Core · ADO.NET

---

## 1. Короткий висновок

FocusLab будується як **локальний монолітний десктопний застосунок** із **багатошаровою архітектурою (Layered / Clean-lite)**, у якій шар представлення реалізовано за патерном **MVVM**.

Ключові рішення:

- **Один процес, одна локальна БД (SQLite), жодних мережевих залежностей.** Усе, що вимагає мережі, винесено за межі релізу.
- **Чотири шари** з односпрямованими залежностями: `App (WPF)` → `Application` → `Domain`, а `Infrastructure` реалізує інтерфейси `Application`.
- **MVVM + Dependency Injection** — View нічого не знає про БД, файлову систему чи ОС.
- **Гібридний доступ до даних:** EF Core для CRUD і міграцій, ADO.NET для аналітичних запитів (`GROUP BY`, `SUM`).
- **Async/await скрізь, де є I/O**, короткоживучі `DbContext` через `IDbContextFactory`.
- **Усі системні виклики (Process.Start, діалоги, сповіщення, годинник) сховано за інтерфейсами**, щоб логіку можна було тестувати без Windows-UI.

## 2. Архітектурні драйвери

Вимоги, які реально впливають на вибір архітектури:

| Драйвер | Вплив на архітектуру |
|---|---|
| **Offline-first**, 100% функціоналу без мережі | Локальна БД, відсутність HTTP-клієнтів, шрифтів і графіків із CDN; ніякої синхронізації в архітектурі першого релізу |
| **Нативна продуктивність**, холодний старт ≤ 2–3 с | WPF замість Electron; легка ініціалізація, міграції та перше звернення до БД виконуються асинхронно до показу головного вікна |
| **UI не блокується** під час збереження і побудови звітів | Async/await у сервісах, оптимістичне оновлення UI, фонове виконання аналітики |
| **Складний інтерактивний UI** (Канбан, Drag & Drop, Pomodoro-індикатор) | MVVM, `ControlTemplate`/`Style`, data binding, команди (`ICommand`) |
| **Інтеграція з ОС** (файли, папки, URL, Windows-сповіщення) | Ізоляція в адаптерах (`IResourceLauncher`, `INotificationService`), обробка винятків без краху застосунку |
| **Гібрид EF Core + ADO.NET замість «один інструмент для всього» |
| **Надійність даних** (єдиний файл БД = усі дані користувача) | Резервне копіювання, коректний режим журналу SQLite, узгоджена обробка помилок запису |
| **Локалізація** (українська, розширення через `.resx`) | Усі рядки UI у ресурсах, жодних захардкоджених текстів у View/ViewModel |
| **Невелика команда, навчальний/портфоліо-проєкт** | Уникати надмірної складності (повний DDD, CQRS, мікросервіси, Event Sourcing) |

## 3. Обраний архітектурний підхід

### 3.1. Стиль: багатошаровий монолітний десктопний застосунок

Застосунок — єдиний виконуваний файл із логічним поділом на шари. Це свідомо спрощена версія Clean Architecture («Clean-lite»): зберігаємо правило залежностей і тестованість, але не вводимо зайвих абстракцій (CQRS, медіатори, окремі read/write-моделі).

```
┌──────────────────────────────────────────────────────────┐
│  FocusLab.App  (WPF)                                     │
│  Views (XAML) · ViewModels · Converters · Styles · .resx │
│  Composition Root (DI), навігація, діалоги               │
└───────────────────────────┬──────────────────────────────┘
                            │ залежить від
┌───────────────────────────▼──────────────────────────────┐
│  FocusLab.Application                                    │
│  Сервіси: TaskService, ProjectService, TagService,       │
│  ResourceService, FocusService,                          │
│  AnalyticsService · DTO · інтерфейси портів              │
└───────────────────────────┬──────────────────────────────┘
                            │ залежить від
┌───────────────────────────▼──────────────────────────────┐
│  FocusLab.Domain                                         │
│  Сутності, enum-и, прості доменні правила                │
│  (без залежностей від EF, WPF, SQLite)                   │
└──────────────────────────────────────────────────────────┘
                            ▲ реалізує інтерфейси Application
┌───────────────────────────┴──────────────────────────────┐
│  FocusLab.Infrastructure                                 │
│  AppDbContext + міграції (EF Core)                       │
│  AnalyticsReader (ADO.NET) · ResourceLauncher            │
│  WindowsNotificationService · SystemClock · Backup       │
└──────────────────────────────────────────────────────────┘
```

**Правило залежностей:**

- `Domain` не посилається ні на що.
- `Application` посилається лише на `Domain` і оголошує інтерфейси (порти), які їй потрібні.
- `Infrastructure` реалізує ці інтерфейси.
- `App` збирає все разом у composition root, посилаючись на всі шари.

## 4. Шар представлення: MVVM

### 4.1. Відповідальності

| Компонент | Відповідальність | Чого не робить |
|---|---|---|
| **View (XAML)** | Розмітка, стилі, анімації, прив'язки | Не містить бізнес-логіки; code-behind — лише суто візуальна поведінка (наприклад, ініціація `DragDrop.DoDragDrop`) |
| **ViewModel** | Стан екрана, команди, валідація введення, виклики сервісів | Не знає про `DbContext`, `Process`, `MessageBox`, `OpenFileDialog` |
| **Model / DTO** | Дані для відображення | — |

### 4.2. Практичні рішення

- **Бібліотека MVVM:** `CommunityToolkit.Mvvm` (`ObservableObject`, `[ObservableProperty]`, `[RelayCommand]`, `AsyncRelayCommand`, `WeakReferenceMessenger`).
- **Навігація:** ViewModel-first — головне вікно містить `CurrentViewModel`, а `DataTemplate` підбирає View. Навігацію інкапсульовано в `INavigationService`.
- **Діалоги** (вибір файлу/папки, підтвердження видалення, помилки) — через `IDialogService`, а не напряму з ViewModel.
- **Міжмодульна комунікація:** `IMessenger` для слабко зв'язаних подій, наприклад «сесію завершено → оновити аналітику», «задачу змінено → оновити дошку».
- **Колекції на дошці:** `ObservableCollection<TaskCardViewModel>` для кожної колонки; пошук і фільтри — через `ICollectionView` (в пам'яті, миттєво).
- **Drag & Drop:** вбудований WPF-механізм (`DragDrop.DoDragDrop`, `AllowDrop`, `Drop`) + attached behavior, щоб View не містив логіки. ViewModel отримує лише `taskId` і нову колонку.

### 4.3. Ключові екрани та ViewModel-и

| Екран | ViewModel |
|---|---|
| Канбан-дошка | `BoardViewModel`, `TaskCardViewModel`, `FilterViewModel` |
| Форма задачі | `TaskEditorViewModel` (валідація: назва 1–255 символів) |
| Ресурси задачі | `ResourceListViewModel` |
| Фокус-режим | `FocusViewModel` |
| Налаштування | `SettingsViewModel` (тривалості сесій, мова, резервна копія) |

## 5. Шар застосунку (Application)

Сервіси містять прикладну логіку і є єдиною точкою доступу ViewModel до даних та системних можливостей.

| Сервіс | Основні операції |
|---|---|
| `TaskService` | Створення, редагування, видалення, `ChangeStatusAsync` (встановлення/скидання `CompletedAt`), фільтрація |
| `ProjectService` / `TagService` | CRUD проєктів і тегів, поведінка при видаленні |
| `ResourceService` | Додавання ресурсу (валідація URL `http/https`), відкриття через `IResourceLauncher` із перевіркою існування |
| `FocusService` | Керування станом сесії, запис завершених сесій, лічильник циклу (4 сесії → довга перерва) |

### 5.1. Таймер Pomodoro

Таймер — окремий **singleton-сервіс** (`FocusService`), а не частина ViewModel екрана. Завдяки цьому сесія не губиться при навігації між екранами і триває при згорнутому вікні.

- Стан у пам'яті: `Idle → Running ⇄ Paused → Break → Idle`.
- Залишок часу **не накопичується лічильником тіків**, а обчислюється як `duration − (UtcNow − startTime − pausedTotal)`. Це робить відлік стійким до затримок потоку, згортання вікна та сну ПК.
- UI оновлюється через `DispatcherTimer` раз на секунду.
- До БД нічого не пишеться, доки сесія не завершена. При завершенні: звук → Windows-сповіщення → `FocusSessions` (`IsCompleted = true`) → перерва.
- Тривалості (25 / 5 / 15–20) беруться з налаштувань, а не зашиваються в код.

### 5.2. Порти (інтерфейси, які реалізує Infrastructure)

| Інтерфейс | Призначення | Реалізація |
|---|---|---|
| `IClock` | Поточний час (UTC), підміна в тестах | `SystemClock` |
| `IResourceLauncher` | Відкриття файлу/папки/URL | `Process.Start` з `UseShellExecute = true` |
| `INotificationService` | Нативні Windows-сповіщення і звук | Toast-сповіщення Windows 10/11 |
| `IBackupService` | Резервна копія файлу БД | SQLite Backup API / `VACUUM INTO` |

## 6. Доступ до даних

### 6.1. Чому гібрид EF Core + ADO.NET

| Сценарій | Інструмент | Обґрунтування |
|---|---|---|
| CRUD задач, проєктів, тегів, ресурсів, сесій | **EF Core** (Code-First) | Типізовані LINQ-запити, автоматичний Change Tracking, міграції, зручна робота зі зв'язками |
| Схема БД і її еволюція | **EF Core Migrations** | Схема описується C#-сутностями, застосовується автоматично при першому запуску |
| Масові операції | **ADO.NET** (за потреби) | Швидше, ніж проходити через Change Tracker |

**Принцип розподілу:** запис і прості читання — EF Core; складні читання для звітів — ADO.NET. **ADO.NET використовується лише на читання**, щоб EF Core залишався єдиним «власником» схеми та записів.

### 6.2. Правила роботи з `DbContext`

- `DbContext` **не потокобезпечний** → реєструється `IDbContextFactory<AppDbContext>`; кожна операція створює короткоживучий контекст (`await using var db = factory.CreateDbContext()`).
- Усі операції — `async` (`ToListAsync`, `SaveChangesAsync`).
- Для читання списків без редагування — `AsNoTracking()`.
- Індекси: `Tasks(Status)`, `Tasks(ProjectId)`, `FocusSessions(StartDateTime)`, `FocusSessions(TaskId)`, `TaskResources(TaskId)`.

### 6.3. Спільний доступ двох стеків до одного файлу SQLite

Щоб уникнути помилок `database is locked` та неузгодженої поведінки:

- **Один рядок підключення**, що береться з одного місця й використовується і EF Core, і ADO.NET.
- Режим журналу **WAL** (`PRAGMA journal_mode=WAL`) — читання аналітики не блокує запис.
- Для ADO.NET-з'єднань явно вмикати `PRAGMA foreign_keys = ON` (EF Core робить це сам, «сирий» ADO.NET — ні).
- ADO.NET-з'єднання відкриваються на час запиту й одразу закриваються.

### 6.4. Модель даних

Схема складається з шести таблиць (імена в БД — `snake_case`; у C# сутність `tasks` називається `TaskItem`, щоб не конфліктувати з `System.Threading.Tasks.Task`).

```
projects 1 ───── N tasks N ───── M tags      (через task_tags)
                    │
                    ├── 1 ─── N task_resources    (File | Folder | Url)
                    └── 1 ─── N focus_sessions
```

| Таблиця | Поля |
|---|---|
| `tasks` | `id`, `title` (varchar 255, NN), `description` (text), `deadline` (datetime), `priority` (enum, NN), `status` (enum, NN), `project_id` (FK, nullable), `created_at` (NN), `completed_at` |
| `projects` | `id`, `name`, `color` |
| `tags` | `id`, `name`, `color` |
| `task_tags` | `task_id`, `tag_id` (складений PK, зв'язок many-to-many) |
| `task_resources` | `id`, `task_id` (FK, NN), `type` (enum: File/Folder/Url, NN), `path` (NN), `display_name` |
| `focus_sessions` | `id`, `task_id` (FK, NN), `start_date_time` (NN), `duration_minutes` (NN), `is_completed` (boolean, NN) |

**Enum-и:** `Priority` (Low, Medium, High, Critical), `TaskStatus` (Todo, InProgress, Review, Done), `ResourceType` (File, Folder, Url).

**Правила цілісності:**

- Видалення проєкту → `Task.ProjectId = NULL` (`ON DELETE SET NULL`), задачі переходять у «Без проєкту».
- Видалення задачі → каскадно видаляються ресурси та зв'язки з тегами; для сесій потрібно ухвалити рішення (див. розділ 10).
- Видалення тегу → видаляються лише записи `TaskTag`.

### 6.5. Розташування даних

- Файл БД: `%AppData%\FocusLab\focuslab.db` (немає проблем із правами запису).
- Логи: `%AppData%\FocusLab\logs\`.
- Налаштування користувача (тривалості таймера, мова): `settings.json` поруч із БД.

## 7. Наскрізні аспекти (Cross-cutting concerns)

### 7.1. Dependency Injection

`Microsoft.Extensions.DependencyInjection` (через `Host.CreateDefaultBuilder` або вручну в `App.xaml.cs`).

| Час життя | Що реєструється |
|---|---|
| **Singleton** | `FocusService`, `IMessenger`, `INavigationService`, `IClock`, `INotificationService`, `IDbContextFactory<AppDbContext>` |
| **Transient / Scoped-за-операцію** | Сервіси прикладного шару, ViewModel-и екранів |

### 7.2. Асинхронність

- Усі операції з БД і файловою системою — `async`/`await`; жодних `.Result` / `.Wait()` на UI-потоці.
- Drag & Drop: **оптимістичне оновлення UI** + асинхронний запис; при помилці — відкат картки в попередню колонку та повідомлення.

### 7.3. Обробка помилок

| Рівень | Підхід |
|---|---|
| Очікувані ситуації (файл не знайдено, некоректний URL, відсутня програма-асоціація) | Явний результат (`Result`-об'єкт або виняток доменного рівня) → зрозуміле повідомлення користувачу |
| Помилки БД | Повідомлення + збереження введених даних у формі; стан UI узгоджується з БД |
| Непередбачені винятки | Глобальні обробники `DispatcherUnhandledException`, `TaskScheduler.UnobservedTaskException`, `AppDomain.UnhandledException` → лог + повідомлення, без аварійного закриття |
| Відкриття ресурсу | Завжди в `try/catch`; будь-який виняток перетворюється на повідомлення, а не крах |

### 7.4. Дата і час

- У БД — **завжди UTC**; у UI — локальний час.
- Межі «сьогодні / тиждень / місяць» обчислюються за локальним часом і переводяться в UTC для запиту.
- Усі звернення до поточного часу — через `IClock`.

### 7.5. Локалізація

- Усі тексти UI — у `.resx` (`Strings.resx` як базові, `Strings.uk.resx` — українська за замовчуванням).
- Додавання нової мови = додавання ще одного `.resx`-файлу без змін у коді.

### 7.6. Логування

`Microsoft.Extensions.Logging` із записом у файл (наприклад, Serilog sink) — без мережевої телеметрії, що відповідає offline-first.

### 7.7. Резервне копіювання

Через WAL «просто скопіювати файл» під час роботи небезпечно. Тому `IBackupService` використовує механізм SQLite Backup API або `VACUUM INTO`, що гарантує узгоджену копію. Це також основа майбутнього експорту/імпорту даних.

### 7.8. Безпека та приватність

- Дані не залишають пристрій; мережевих запитів застосунок не робить (крім відкриття URL у браузері користувача).
- Окремої автентифікації не потрібно: застосунок однокористувацький і локальний.

## 8. Ключові потоки взаємодії

### 8.1. Перший запуск

```
App.OnStartup
  → побудова DI-контейнера
  → створення каталогу %AppData%\FocusLab (за потреби)
  → await db.Database.MigrateAsync()      ← до показу головного вікна
  → показ MainWindow → BoardViewModel.LoadAsync()
```

Якщо немає прав запису в каталог — повідомлення та резервне розташування. Якщо БД пошкоджено — пропозиція створити нову (з попередженням).

### 8.2. Зміна статусу задачі (Drag & Drop)

```
View (Drop) → BoardViewModel.MoveTaskCommand(taskId, newStatus)
  → оптимістичне переміщення картки в UI
  → TaskService.ChangeStatusAsync()
        Done → CompletedAt = UtcNow
        Done → інший статус → CompletedAt = null
  → помилка → відкат картки + повідомлення
```

### 8.3. Відкриття ресурсу

```
Клік → OpenResourceCommand(resource)
  → URL: перевірка http/https → Process.Start (UseShellExecute = true)
  → File/Folder: File.Exists / Directory.Exists
        існує → Process.Start
        не існує → повідомлення «Файл за шляхом ... не знайдено»
  → увесь виклик у try/catch
```

### 8.4. Завершення фокус-сесії

```
FocusService (00:00)
  → INotificationService: звук + Windows-сповіщення
  → запис FocusSession (TaskId, StartDateTime, DurationMinutes, IsCompleted = true)
  → лічильник циклу: < 4 → коротка перерва; = 4 → довга перерва, скидання лічильника
  → Messenger: SessionCompleted → AnalyticsViewModel оновлює дані
```

| Варіант | Плюси | Мінуси | Рішення |
|---|---|---|---|
| **WPF + MVVM** *(обрано)* | Нативна швидкість, зрілий data binding, потужна стилізація, відмінна тестованість ViewModel | Лише Windows, немає готового Канбан-контролу | ✅ Підходить: цільова платформа — Windows, потрібна продуктивність |
| Electron / веб-стек | Кросплатформність, багата екосистема UI | Височе споживання RAM, повільніший старт, суперечить ціннісній пропозиції «нативна швидкість» | ❌ |
| WinForms | Простота | Слабка стилізація, складний сучасний UI, немає повноцінного binding | ❌ |
| MAUI / Avalonia | Кросплатформність | Менша зрілість для складного десктопного UI, ширший обсяг навчання, не потрібно для поточної цілі | ❌ (можна розглянути як майбутню міграцію) |
| **Layered / Clean-lite** *(обрано)* | Чіткі межі, тестованість, зрозумілість для невеликої команди | Трохи більше «церемонії», ніж один проєкт | ✅ |
| Один проєкт без шарів | Найшвидший старт | Змішування UI, логіки й даних; складне тестування; важко ростити | ❌ |
| Повний DDD + CQRS + MediatR | Масштабованість для складних доменів | Надмірно для доменної складності цього застосунку | ❌ |
| Лише EF Core | Один інструмент, простіше | Менш ефективний для агрегатних звітів; не демонструє роботу з сирим SQL | ❌ |
| Лише ADO.NET | Максимальний контроль | Ручний маппінг, відсутність міграцій і Change Tracking, багато шаблонного коду | ❌ |
| **EF Core + ADO.NET** *(обрано)* | Кожен інструмент — для своєї задачі | Потрібно узгодити підключення та режим журналу | ✅ |
| Клієнт-серверна архітектура / хмарна БД | Синхронізація між пристроями, багатокористувацький режим | Суперечить offline-first, значно ускладнює проєкт | ❌ (поза межами релізу) |

### Питання, які ще потрібно вирішити

| Питання | Рекомендація |
|---|---|
| Що записувати при достроковій зупинці сесії? | Записувати `IsCompleted = false` із фактичною тривалістю, а в аналітиці рахувати лише завершені (або явно показувати обидва) |

## 11. Технічні ризики та заходи

| Ризик | Заходи |
|---|---|
| Нативні Windows-сповіщення не працюють «з коробки» у WPF | Підключити NuGet-пакет для toast-сповіщень, використати target framework `net8.0-windows10.0.xxxxx`; перевірити **на самому початку** |
| Відсутність готового Канбан-контролу | Закласти час на `DragDrop`, візуальний фідбек, attached behaviors |
| Блокування БД при спільній роботі EF Core і ADO.NET | WAL, єдиний рядок підключення, короткі з'єднання |
| Холодний старт > 2–3 с | Виміряти рано; асинхронна ініціалізація БД; не робити важких операцій до показу вікна |
| Втрата файлу БД = втрата всіх даних | Резервне копіювання, у перспективі — експорт/імпорт |
| Помилки часових поясів у звітах | UTC у БД, межі періодів рахувати в локальному часі й переводити в UTC |
| Зниклі файли/папки, прикріплені до задач | Перевірка існування в момент кліку, а не при завантаженні дошки |
| Зростання складності ViewModel | Дрібні ViewModel-и на екран/компонент, логіка — у сервісах |

## 12. Тестування

| Рівень | Що тестується | Інструменти |
|---|---|---|

## 14. Підсумок

Обраний підхід — **багатошаровий (Clean-lite) монолітний WPF-застосунок із MVVM, DI, SQLite та гібридним доступом до даних (EF Core + ADO.NET)** — найкраще збалансовує:

- **автономність і швидкість** (локальна БД, нативний UI, async-операції);
- **підтримуваність і тестованість** (шари, інтерфейси, прикладні сервіси, тонкі ViewModel-и);
- **розумну складність** для невеликої команди (без CQRS, мікросервісів та надлишкових абстракцій);
- **можливість розвитку** (нові модулі додаються вертикальними зрізами; потенційну синхронізацію чи міграцію UI можна розглянути пізніше без переписування доменного та прикладного шарів).
